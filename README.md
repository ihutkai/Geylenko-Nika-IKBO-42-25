## Этап 1. Минимальный прототип с конфигурацией

### Шаг 1. Чтение корректных настроек

Настройки хранятся в [config.json](config.json):

```json
{
  "package": "express",
  "repository": "https://registry.npmjs.org",
  "test_mode": false,
  "ascii_tree": false,
  "max_depth": 3
}
```

| Параметр | Значение и назначение |
| --- | --- |
| `package` | Имя анализируемого пакета; здесь `express` |
| `repository` | URL реестра npm; в тестовом режиме — путь к файлу |
| `test_mode` | `false` — реальный реестр; `true` — тестовый файл |
| `ascii_tree` | Настройка вывода ASCII-дерева; сам вывод относится к этапу 5 и здесь не реализуется |
| `max_depth` | Максимальная глубина анализа, целое число не меньше 0; корень имеет глубину 0 |

Запуск:

```powershell
python src/main.py --config config.json --stage 1
```

![Корректное чтение пяти настроек](screenshots/01-config-success.png)

**Результат и объяснение:** программа прочитала JSON, проверила значения
и вывела все пять параметров в формате ключ-значение. `False` в выводе Python
соответствует `false` в JSON. Этот вывод — требование первого этапа;
анализ зависимостей пока не производится.

`--config` задаёт только путь к файлу; все пять пользовательских настроек

## Этап 2. Получение прямых зависимостей npm

В терминале VS Code из папки проекта:

```powershell
python src/main.py --config config.json
```

По умолчанию демонстрируется этап 2. Параметр `--stage 1` сохраняет возможность
показать только настройки первого этапа, `--stage 2` явно выбирает второй.
Пять пользовательских настроек по-прежнему читаются из JSON.

Программа отправляет HTTP GET по адресу `<repository>/<package>/latest`,
читает JSON и самостоятельно извлекает `dependencies` — прямые рабочие
зависимости выбранного пакета. Выводятся версия пакета, количество зависимостей,
их имена и заявленные диапазоны версий. Используются только стандартные модули
Python `urllib` и `json`. npm, pip и сторонние библиотеки для получения
зависимостей не вызываются. Поле `devDependencies` не анализируется.
Диапазоны версий печатаются без разрешения в конкретные версии.

Источник описания API: [официальная документация npm Registry API](https://github.com/npm/registry/blob/main/docs/REGISTRY-API.md).

`src/registry.py`: `get_dependencies()` получает JSON по HTTP;
`parse_metadata()` проверяет ответ и извлекает зависимости;
`RegistryError` описывает ошибки сети, HTTP и формата ответа.
Пакет без `dependencies` выводится с сообщением об отсутствии зависимостей.
HTTP 404, недоступность сети, таймаут и некорректный JSON обрабатываются
понятными сообщениями и кодом завершения 1. Нужен доступ в интернет.

Тестовый граф пока не используется: для этапа 2 нужно `test_mode: false`.
Глубина и настройка ASCII-дерева ещё не влияют на вывод прямых зависимостей.
Версия `latest` и список зависимостей могут меняться со временем.

`tests/test_registry.py` проверяет HTTP-запросы на подставных ответах,
кодирование scoped-имён, обработку метаданных, отсутствие зависимостей,
ошибки сети и неверный JSON. Всего после добавления этапа 2 — 12 тестов.

## Этап 3. Граф зависимостей, DFS без рекурсии

Этап выбирается явно через `--stage 3`. Запуск без `--stage` по-прежнему
показывает прямые зависимости этапа 2. Все пять настроек берутся из JSON.

### Тестовый граф с общей зависимостью

```powershell
python src/main.py --stage 3 --config examples/test-config.json
```

В `test-repository.json`: A зависит от B и C; B и C зависят от D;
у D нет зависимостей. Порядок DFS: A, B, D, C. Общий пакет D не дублируется,
при этом сохраняются оба ребра B → D и C → D.

### Максимальная глубина

```powershell
python src/main.py --stage 3 --config examples/depth1-config.json
python src/main.py --stage 3 --config examples/depth0-config.json
```

При глубине 1 включены A, B и C; зависимости B и C не запрашиваются.
При глубине 0 включён только A. Корень имеет глубину 0.
Для каждого узла показывается минимальное расстояние от корня.
Если DFS сначала дошёл по длинному пути, а затем нашёл короткий,
узел расширяется повторно с учётом оставшегося лимита глубины.

### Циклические зависимости

```powershell
python src/main.py --stage 3 --config examples/cycle-config.json
```

Цикл A → B → C → A выводится отдельно, программа завершается нормально.
Обход хранит уже достигнутые глубины и не следует по циклу бесконечно.
Циклы ищутся итеративным DFS с цветами и активным путём в исследованных рёбрах.
Циклы за границей заданной глубины могут не попасть в построенный граф.
Вывод показывает найденные свидетельства циклов, а не перечисляет все
возможные простые циклы в сложном графе.

### Пакет без зависимостей и неверный тестовый граф

```powershell
python src/main.py --stage 3 --config examples/isolated-config.json
python src/main.py --stage 3 --config examples/bad-graph-config.json
```

Первый пример содержит только A. Во втором A ссылается на отсутствующий B:
программа сообщает ошибку структуры тестового репозитория.
Формат тестового файла — JSON-объект: имя пакета из больших латинских букв
соответствует списку имён зависимостей. Все имена зависимостей должны быть
объявлены ключами. Повторы ключей и рёбер запрещены.

### Работа с реестром npm

```powershell
python src/main.py --stage 3 --config examples/npm-depth1-config.json
```

Это граф express с глубиной 1. Для более глубокого обхода можно увеличить
`max_depth` в отдельной конфигурации. Для каждого раскрываемого имени берутся
метаданные `latest`, ответы кэшируются в пределах запуска.
Это граф зависимостей по именам пакетов: разные версии одного имени
не представлены отдельными узлами, диапазоны SemVer не разрешаются.
Он не является точной моделью дерева установленного npm-проекта.
Ошибки сети останавливают построение с понятным сообщением.

### Реализация и тесты

`src/graph.py`: `build_graph()` строит граф с помощью списка-стека;
`find_cycles()` обнаруживает циклы также без рекурсии;
`load_test_graph()` читает и проверяет тестовый JSON;
`analyze()` выбирает источник данных; `GraphResult` хранит результат;
`print_graph()` выводит связи и глубины. Вывод списка связей не является
ASCII-деревом или визуализацией этапа 5; `ascii_tree` пока не используется.
Обратные зависимости этапа 4 и визуализация этапа 5 не реализованы.

После добавления этапа 3 выполняется 21 автоматический тест:

```powershell

```

Проверяются общие зависимости, глубина 0 и 1, обычный цикл, петля,
более короткий путь к ранее посещённому узлу, цепочка из 1501 узла
без рекурсии, повреждённые графы, кэш HTTP-провайдера и запуск CLI.
